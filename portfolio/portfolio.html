linebender/resvg · #1134

Tracing lost gradient transforms to a regression

Bug reporter · regression analysis and merged fix

Opened 2026-09-13 Closed 2026-10-03

Resolved through my merged PR

The problem

A gradient or pattern using another as a template through href inherited stops, coordinates, units and spreadMethod, but not gradientTransform or patternTransform. In my minimal SVG, a gold-to-navy gradient whose template is rotated 90 degrees rendered left to right in resvg instead of top to bottom. Issue report

Why it was needed

SVG 2 explicitly lists these transforms among the attributes copied from a template, and SVG 1.1 states the rule generally. The report showed the same loss for a radial gradient translation and a rotated pattern, so documents that reuse paint servers could render incorrectly. Issue report

My contribution and the resolution

I traced the cause to 9101f30a, the transform-origin change first released in v0.37.0: resolve_transform reads only the element itself, leaving the href-aware GradientTransform lookups unused. I proposed resolving the defining element first, attached before/after renders compared with rsvg-convert, and opened #1135, whose merge on October 3, 2026 closed the issue. Issue report · Resolution

Why this approach

Rather than patching the symptom, the report compared the v0.36.0 converters with the current ones and noted that no existing attributes-via-xlink-href test set a transform on the referenced element, explaining why the regression went unnoticed. The proposal keeps transform-origin support and lets a local transform win. Issue report

Validation and outcome

My pixel comparisons (within 1/255 after the fix, up to 255 before) are author-reported. Independently, matthargett commented that a new WPT reftest covers this case, that usvg 0.48.1 renders it untransformed, and that Chromium 131 and Firefox agree on the expected output. LaurenzV closed the issue on 2026-10-03. Issue report · Discussion · Resolution

Pull request author · upstream contribution

Opened 2026-09-06 Merged 2026-09-21

The problem

Why it was needed

Containment should be symmetric about the cylinder's Z axis. Adding Y twice instead of squaring it made the answer depend on the sign of Y and accepted arbitrarily negative Y when X and Z were zero, so the error was not confined to boundary points. Companion report #29 documents the standalone reproducer. PR record · Issue report

The accepted change is one line in Physics3D/geometry/builtinShapeClasses.cpp: y + y becomes y * y, so the radial check reads x*x + y*y <= 1.0 beside the unchanged abs(z) <= 1.0 cap test. No other file, signature or shape class changed. The PR was opened about a minute before I filed #29, and its body links that issue with Fixes #29. Changed files · Issue report

Why this approach

Documented: the PR frames the defect as broken cylinder symmetry and restores the squared term. Implementation-derived: correcting the shared shape-class predicate fixes every containsPoint caller for cylinders at once, without touching the separate intersection-distance code below it in the same file. PR record · Changed files

Validation and outcome

Author-reported: a Debug build with GCC 16.0.1 passed all 13 geometry tests, and a local 30-assertion regression test over both signs of X and Y, two radii, and radial and cap boundaries failed before the fix and passed after. The problem
